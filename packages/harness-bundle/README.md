# harness-bundle

The harness bundle of Bowerloom 0.8: the one file a harness travels in (spec section 6.7). This package encodes a loaded definition into a bundle, decodes and checks a bundle, says what it holds, builds the target files of an import, and reads and writes the bundle file with bounds. `bowerloom harness export` and `bowerloom harness import` and the app's Export and Import sheets all call it.

Status: stage 2 lane A. Every function in `src/index.ts` is built to the contract of stage 1. The types and signatures did not change; since the stage 1 contract the code table grew by `BUNDLE_FILE_FAILED`, and the words of `IMPORT_FOLDER_HAS_HARNESS` say "parts or settings".

## The file

- Format `bowerloom/harness-bundle/v1beta1`. UTF-8 JSON, one object, no compression, no archive. 2-space indent and one final line feed, so it reads and diffs as text.
- Keys in this order: `format`, `harness`, `generator`, `revision`, `files`, `knowledge`. The writer always writes this order; the reader accepts any order, but `files` must be in byte order of path (so one harness has one file). The shapes are in `src/types.ts` (`BundleEnvelope`, `BundleFileRecord`).
- A file record has `path`, `size`, `sha256`, `encoding` (`utf8` or `base64`), `data`, and `executable: true` only when the file has an execute bit. Files sort by path in byte order. `encodeBundle` writes a record as `base64` when that is smaller than the escaped text.
- The file never holds `knowledge.json` (paths stay on the computer they belong to), a secret value, the home path of the exporter, or a path the exporter added. A notes source travels as a kind and a name.
- Unknown keys anywhere are refused. A key such as `type`, `link`, `target`, `mode` or `owner` fails.
- `revision` is `sha256:` plus the definition revision of the decoded files. It catches damage and edits. It is not a signature: a person who forges a bundle can set a matching revision. Validation, not the hash, is the defence. It is the one prefixed revision. Every plan revision (`ExportPlan`, `ImportPlan`, the app's views) is bare lowercase hex.
- `generator` is informational. Bowerloom never trusts it.
- The execute bit is not covered by `revision` (it hashes paths and contents, as `computeRevision` does everywhere) nor by the `sha256` of a record. Only the `sha256` of the whole bundle file binds it, which is the hash a plan holds. So a bundle edited to add or remove `"executable": true` is accepted by `decodeBundle`, and the protection is the acknowledgement: it lists every file written with an execute bit, and the person ticks it.

## What the package does

- `encodeBundle(def, options)` and `decodeBundle(bytes)`. Both are async and pure. They take a turn of the event loop between files (after about 12 ms of work), which shortens the stalls of their own loops. They do not make a bundle safe to process on the main thread of an app: the load of the files as a harness (with the secret scan), the summary and the revision are single synchronous calls (see Where to run it).
- `inspectBundle(bundle)`: counts, tools (with their whole command, all their arguments, environment, headers, url path, host, hook text and a hash of the whole entry), files that run code (with hashes), the references the file reads from this computer and where each one goes, notes names, borrowed items, and text that holds a path of another computer (with the text and its hash). `counts.bytes` is the size of the decoded files, not of the bundle file (`DecodedBundle.bytes` is that).
- `targetFromBundle(bundle, choices)`: the files an import writes. A notes name is linked to a stored path or left out. A name in neither is left out. It runs `editDefinition` with a `set-source` for each linked name and a `remove-source` for each other name, so the result loads.
- `isEmptyHarness(def)`, `harnessPartsFound(def)` and `assertEmptyHarness(def)`: a harness is empty when it holds no entry, no instructions, no source, no knowledge, no script and no engine file. A script, an engine file and a converted skill count as parts, because the save an import makes would delete them. So do the settings in `harness.json` that a person made: a description other than `EMPTY_HARNESS_DESCRIPTION` (what "Make an empty harness here" writes; one constant in `packages/harness-definition/src/defaults.ts`, used by adoption and exported here, so the app and the command line do not copy it), an engine with a version or a model, an override, and the settings of a skill. A plain list of engines alone does not count, because a new harness lists the engines found. **A harness with settings only is not empty (decision of the owner, 2026-11-01):** an import into it is refused `IMPORT_FOLDER_HAS_HARNESS`, and `assertEmptyHarness` names in the refusal's `paths` each part or setting found (`skills`, `a description you wrote`, `an engine with a version or a model`, `an override`, `settings of a skill`, …). `isEmptyHarness` fails closed: a value that is not a definition is not empty. Adoption writes `version` and `model` for an engine whose config names one, so a harness made empty in such a project reads as not empty and an import into it is refused, with the engine named.
- `addressOf(url)` and `codeWhy(path, bytes, executable)`.

How `decodeBundle` checks, in this order, and the code of each refusal: the size (`BUNDLE_TOO_LARGE`); a byte order mark or text that is not UTF-8 (`BUNDLE_FORMAT`); strict JSON, at most six levels deep and about 33,000 values (`BUNDLE_FORMAT`, or `BUNDLE_TOO_LARGE` for the number of values); the closed shape and the names (`BUNDLE_FORMAT`; more files or notes names than the limit are `BUNDLE_TOO_LARGE`); every path (`BUNDLE_PATH_UNSAFE`, two paths that clash included); the order of the files (`BUNDLE_FORMAT`) and the declared sizes (`BUNDLE_TOO_LARGE`); the bytes of each file against its size and hash (`BUNDLE_DAMAGED`); the secret scan and the load, both by `loadDefinitionFiles` with a placeholder source for each notes name (`BUNDLE_SECRET_FOUND`, `BUNDLE_TOO_LARGE`, `BUNDLE_INVALID`); the harness id against the one loaded and the revision (`BUNDLE_DAMAGED`). Any other fault is `BUNDLE_FORMAT`, so nothing but a `BundleRefusal` leaves it. The placeholder paths are fixed text inside the harness folder (`bundle-notes/<name>`); nothing reads them, and they never leave in a bundle or a target.

Foreign paths: the list covers an absolute path under a known root (`/Users`, `/home`, `/root`, `/Volumes`, `/mnt`, `/media`, `/private`, `/tmp`, `/var`, `/opt`, `/srv`, `/usr`, `/bin`, `/sbin`, `/etc`, `/Applications`, `/Library`, `/nix`, `/snap`), a home path (`~/`), a drive path (`C:\`, `C:/`, and the JSON-escaped form), a file URL, and, when the caller gives them in `EncodeOptions`, the home folder and the user name of the exporter, matched literally. A path inside a URL does not match, and a standard interpreter on a `#!` line (`/usr/bin/env`, `/bin/sh`, …) is not a hit. Only text files are scanned as text; a file that is not UTF-8, or holds a NUL, is read as bytes (a path is ASCII, so it is found), but UTF-16 text is not. One file lists at most 100 hits, then one line says there are more and the scan goes on with the next file; the bundle lists at most 1,000, and then the list ends with one line, `More paths of this kind were found and are not listed.`, which the acknowledgement covers. The summary from `inspectBundle` has no `home` or `user`, so its list can be shorter than the one `encodeBundle` returned when those options are set. A `user` of fewer than 3 characters and a `home` of one character are ignored, because they would match ordinary text.

## Addresses and files that run

- A tool's host is the host a client would really reach. `addressOf` masks each `${NAME}`, parses the address with `URL`, and shows `hostname` plus `:port`. So `https://github.com:${TOKEN}@evil.example/` shows `evil.example` and the flag `credentials`; a backslash address shows the host a client reads and the flag `backslash`; `https://[::1]:8080/` shows `[::1]:8080`; an address that does not parse shows `unreadable address`.
- The signature check of an image or a font is a prefix check: the bytes must begin with the kind's own signature, and the rest is not parsed. A real PNG header followed by a script is data by this list, and so is any file whose first bytes look right. That is a stated limit, not a defence; the list is a screen, not a proof (round 5, L5-2).
- A file is data only when it passes an allowlist; every other file can run and is listed with its hash. Data: a name that ends in `.md .markdown .txt .rst .json .jsonc .yaml .yml .toml .csv .tsv .css` (valid UTF-8 with no NUL), or a file named README, LICENSE or NOTICE with no extension; or `.png .jpg .jpeg .gif .webp .ico .woff .woff2 .ttf .otf` whose bytes begin with that kind's own signature (anything else under such a name is listed as `binary`). All in any case, with no trailing space or dot, whose first bytes (after any number of UTF-8 byte order marks) are not `#!`, ELF, Mach-O or WebAssembly, and (for a file that is not text) not PE (`MZ`, two bytes, so a note that begins with "MZ" is not taken for a program). A manifest that tells a tool which commands to run (`package.json`, `pyproject.toml`, `Cargo.toml`, `composer.json`, a compose file, `Taskfile.yml`, `justfile`, `Makefile`, `Dockerfile`, and the configs of a runtime, a host or a pipeline: `deno.json`, `requirements.txt` and `requirements-*.txt`, `vercel.json`, `netlify.toml`, `action.yml`, `serverless.yml`, `azure-pipelines.yml`, `wrangler.toml`, `fly.toml`, `turbo.json` and others, see `MANIFEST_NAMES`) is listed as `manifest`. `.pdf`, `.html` and `.svg` are listed: they can carry script. So `skills/x/run.sh`, `helper.node`, `setup.hta`, a file with no extension, an `.svg`, `a.sh ` and a Mach-O file named `helper` are all listed and ticked, and `run.sh.txt` is data until it begins with `#!`. The execute bit, `hooks.json` and `scripts/` count first. Missing bytes count as code; the function never throws.
- This list is a screen, not a proof. A tick means "I read what was listed". A text file can hold commands that a tool may run when an agent is told to run it (`curl x | sh` in a note), and nothing here detects that.
- `readBundleFile(absPath)`, `bundleTargetIdentity(absPath)` and `writeBundleFile(absPath, bytes, options)`. All async.

Built now, because they depend on the summary only: `exportAcknowledgement(summary, revision)`, `importAcknowledgement(summary, executables, revision)` and `importChoicesOf(raw, names)`.

An import is a save. The only write is `applySave` in `packages/adoption`, under the project lock, with its journal. This package never writes a harness file.

## Acknowledgements

A tick covers what the person was shown, and the hash binds it.

- `importAcknowledgement` hashes the save plan's revision and: every tool that runs code (a stdio MCP server, a hook) or reaches a host (a remote MCP server) by kind, name and the hash of its whole entry, so a bundle with only an `mcp.json` still needs a tick; every reference in a url, an argument, a command or a header; every file that can run by path and hash; every file written with an execute bit (a sorted, unique list); and every foreign-path hit by path, line and the hash of its text. It is null when all of them are empty.
- `exportAcknowledgement` hashes the plan's revision and the foreign-path hits. It is null when there are none.
- A reference in an `env` value alone adds nothing to the hash of references: `env` applies to a stdio server, which runs code and is ticked as a tool. A reference in a header does need a tick of its own, because a header goes to the host the file names. Every sink shows on screen.
- What the tick binds is what the person sees. The hash of a tool covers its whole entry, so the summary shows the whole entry that matters (see Tools are shown whole): the command, every argument, the environment of a stdio server, the headers and the url of a remote one.

## References are a way out for values

A `${NAME}` reference tells the engine to read a value from this computer and give it to the tool. The name may be set on this computer already. A hostile file can place `${GITHUB_TOKEN}` in a url, an argument, a command or a header, and the value goes to the host the file names. So the summary lists each reference with its sinks: the tool, the field (`env`, `header`, `arg`, `url`, `command`) and the host. The screen says that the file reads these values from this computer and passes them to these tools. It never tells a person to create a variable without showing where it goes. The package does not read an environment variable or the keychain, and it does not check that a listed name exists.

## Where to run it

Decode, encode, `inspectBundle` and `targetFromBundle` do work that cannot take turns: the loader parses every file and scans it for secrets in one synchronous call, and the summary and the revision hash all the bytes. For the largest bundle that is honest (41 MiB of binary files) the longest stretch without a turn was about 350 ms; for 4,000 files of text, about 0.8 s; for the worst bundle that passes the work budgets below, about 2.2 s (measured: 31 MiB of `token: abc` lines, 2.1 s; a mixture that uses every budget, 2.4 s with a longest stretch of 2.2 s). So **the app's main process must not call these functions on its own thread.** Run them in a worker thread or a utility process, give the call a time limit of about 20 s (terminate the worker and answer `BUNDLE_TOO_LARGE`), and pass the bytes to the worker as a transferable buffer, never decoding in the main thread.

- Every function takes plain input (a path string, a `Uint8Array`, plain objects, a `Map` and a `Set` for the choices) and gives plain output. The package imports nothing of Electron, and nothing here uses a global of the main process. Bytes can be passed to a worker as a transferable buffer.
- A `DecodedBundle` is a frozen plain object and crosses a boundary by structured clone, but the copy loses the loaded definition that `decodeBundle` remembers, so `inspectBundle` and `targetFromBundle` on the copy load the files again (seconds, for a large bundle). So the worker that decodes also builds the summary (`inspectBundle`) and, at import time, the target (`targetFromBundle`), and sends back the summary and the files, not the bundle for a second call on the other side.
- A refusal does not survive a structured clone whole (an error drops its extra fields). Send `refusal.toJSON()` and rebuild with `BundleRefusal.fromPlain(value)`, which checks and cuts every field.
- The file functions (`readBundleFile`, `writeBundleFile`, `bundleTargetIdentity`) are asynchronous system calls and do not stall the loop. A read from a stalled network share holds one of the four threads of the file pool; four such reads would hold all file work of the process.

## Work budgets

Two costs of the loader depend on the content and not only on the size, and both are bounded before the loader runs (`src/work-budget.ts`; over either, `BUNDLE_TOO_LARGE`):

- YAML: at most 512 KiB in all of `.yml` and `.yaml` files and the frontmatter blocks of `.md` files. The block is found by the loader's own rule: a first line `---` (spaces and tabs allowed after it) and the next such line, so a line such as `---x: 1` cannot end the count early. A YAML parse costs about 0.7 microseconds a byte, and each of these is parsed more than once. The frontmatter reader also checks for a repeated key in one pass over the parsed document (it was a check of each key against every earlier key, which took 340 ms for one block of 5,500 keys).
- The secret scan: at most 3,000,000 places where the scan does work that depends on the content: each start of a run of letters and digits in a token of 8 or more characters, and, for each token that holds a `:` or an `=`, one place and one more for each `?` and `&` in it. Tokens end where the scanner ends them (white space of JavaScript's `\s`, quotes, brackets, commas, semicolons, bars, backslashes; not U+0085 and not the other control characters); a file the scanner reads as bytes counts only the first kind. Prose has few; text such as `a?a=a?a=…` has about 0.8 million a megabyte, and 31 MiB of it took 7.4 s before.
- Measured with these budgets (this machine, in a worker; the reviewer's cases): 40 skills of 62 KiB frontmatter, 92 ms (refused); 20 skills behind `---x: 1`, 84 ms (refused); 31 MiB of `a?a=` text, 180 ms (refused); the same with U+0085 or U+0001 inside the line, 80 to 170 ms (refused); 31 MiB of `k: v` lines, 240 ms (refused); and, accepted, 8 skills of 5,500 keys, 0.65 s; 3 MiB of `a?a=`, 0.9 s; 31 MiB of `token: abc`, 2.1 s; the mixture of every budget plus filler up to 30 MiB, 2.4 s.

The numbers are the bound, not a promise of the time: the time depends on the machine.

## Tools are shown whole

The acknowledgement binds the whole entry of each tool that runs code or reaches a host, so what a person reads must be the whole entry. The summary therefore carries, whole and never cut:

- an MCP command, every argument, and a hook command (`command`, `args`);
- **the environment of a stdio server** (`env`: one `{ name, value }` row for each variable, in file order). The environment is part of what runs: `NODE_OPTIONS=--import=data:text/javascript,…`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `PATH` (a file of the bundle's `scripts/` ahead of the real one), `BASH_ENV`, `PYTHONSTARTUP` and `JAVA_TOOL_OPTIONS` all start code. A name is listed also when its value is a `${NAME}` reference (shown as written) or a keychain reference (shown as its JSON, `{"keychain":"entry"}`);
- the headers of a remote server (`headers`, the same rows; they go to the host the file names);
- the path, query and fragment of a remote server's url (`path`, as written, next to `host`). An address that does not look like `scheme://authority…` is shown whole as `path`, so nothing is hidden.

`timeout` and `enabled` are bound by the hash and are not shown; they cannot start code.

If any text of these (a command, an argument, a variable or header name or value, a url, a hook command) is longer than 4,000 characters (`BUNDLE_LIMITS.commandChars`), or a server has more than 64 arguments, variables or headers (`toolArgs`), the bundle is refused `BUNDLE_INVALID` on decode and on encode. The refusal's paths read `a tool's command or arguments are too long to show in full (mcp.json: <name>)`, and its problems carry the code `TOOL_TEXT_TOO_LONG`. The command itself is not repeated. A host is still cut to 200 characters (a valid host name is shorter than that). The app's `SHARE_ARGS_LIMIT` is 64 and `SHARE_COMMAND_LIMIT` is 4000, and its views must not cut a command, an argument, a variable, a header or a path (`ShareTool.env`, `.headers` and `.path` carry them).

## Trust boundary

A bundle from another person is data. Reading one starts no program and loads no code.

- `decodeBundle` is bounded: the file size is checked before a read, the JSON is strict (no duplicate key, no `__proto__`, depth at most `BUNDLE_LIMITS.jsonDepth`), shapes are closed, and each declared size is checked against the decoded bytes (the base64 length first).
- The path grammar adds to `plainPath`: a segment that ends in a dot or a space (the save accepts such a name, so a harness that has one can be saved but not exported; the refusal is safe and rare, and stated here), a lone surrogate, and `knowledge.json` in any case. It does not refuse a Windows device name (`con.md`): the save accepts one, and one rule serves both. Two paths that name one file under the shared fold (`foldName` in `packages/harness-definition/src/fold.ts`, also used by the save) clash: `straße` and `strasse`, `ας` and `ασ`, `Skills/a` and `skills/b`, an NFD and an NFC form, a full-width form. The grammar is at least as strict as `planSave`'s `plainPath`: no empty, `.`, `..` or hidden segment, no backslash, no control, format, bidirectional or line-separator character, at most 1,024 characters and 255 bytes per segment, no 0.7 top-level name, no `knowledge.json`, depth at most 16, and no two paths equal under case or Unicode folding.
- A bundle path is only ever a key into `.bowerloom`. No other code turns one into a file system path.
- A hook, a script, an executable file and an MCP command are data. The package spawns nothing, evaluates nothing and imports nothing at run time. A static test checks the source for `child_process`, `vm`, `eval`, `Function(` and `import(`.
- Secrets: a literal secret value refuses the bundle (`BUNDLE_SECRET_FOUND`) on export and on import. References stay: `${NAME}` and `{ "keychain": "<entry>" }`. They are listed with their sinks. The scan covers the text of every file and the file names (each name is one line). It does not find a token split by a NUL, written in UTF-16, encoded in base64, or reversed; that is a stated limit of the scan, not a promise.
- Notes names are untrusted keys. `constructor` is a valid name. Choices are a `Map` and a `Set` (`ImportChoices`), built by `importChoicesOf` from own properties only.
- Refusals: a message holds the table sentence and at most 20 paths. Each path is cut to 120 characters with an ellipsis, and its control, format and line-separator characters are escaped. So a path in a message is quoted text of bounded size. It is not a promise that no text from the file appears. No other text from a file is repeated, and `BundleRefusal.paths` holds the shortened form only.
- Display: every string that came from a file is for a person to read, so the app passes it through `visible()` in main and the command line through `plainText()`.
- The read: `readBundleFile` opens with `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, calls `fstat` on the descriptor, and refuses anything that is not a regular file of the user. A symlink in a folder ABOVE the file is followed (`O_NOFOLLOW` covers the last name only; the write refuses a linked parent with `realpath`). A file of another user is refused too (a shared volume may hit this; the words say "that you own").
- Race windows, named as `save.ts` names its own: the bundle file can change between the open and the end of the read (the identity and size are checked after the read), and the export folder can change between the temporary file and the rename (the target identity is checked again right before it).

## What the callers must do

- The app's main process (lane C) validates every argument of every share call before it uses one: a bundle id against `SHARE_BUNDLE_ID` and looked up by the exact string in a `Map`, never by `Number()`; the choices shape with `importChoicesOf`; every notes id against the ids main gave out; the name and count limits; the revision and the acknowledgement as 64 lowercase hex characters (or null where allowed).
- Main enforces `SAVE_EXECUTABLE_UNACKNOWLEDGED` itself. `applySave` does not check an acknowledgement.
- Main computes the acknowledgement from the summary of the bundle it holds, built in the same call by `inspectBundle`, and never from a summary or a field the window sent. The hash covers each tool's `sha256` and not its shown fields (`command`, `host`, `addressFlags`), so a summary with edited shown fields and the old `sha256` gives the same hash; the rule keeps that from mattering.
- Main compares the acknowledgement it computes now with the one it receives, with the plan revision and the bundle hash it holds, and writes only when all three match.
- Main passes `replace` only when the file existed when the save dialog returned, the person agreed to replace it, and `bundleTargetIdentity` still gives the same identity. Main passes the real path of the target folder (`realpath`), so the person sees the folder that is written.
- The command line replaces a file only with `--replace`, and then only the file it saw when it planned: it passes the identity from `bundleTargetIdentity` as `replace`. Without it, it never replaces a file.

## The file functions: what lane A builds to

- `readBundleFile`: `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`; `fstat` on the descriptor before any read (a folder also opens with `O_RDONLY`); a regular file of the user, at most 48 MiB; read at most one byte past the size; a short read or a read past the size refuses; the identity and size are compared again after the read.
- `bundleTargetIdentity`: `lstat` with `bigint: true`. The identity is `dev`, `ino`, `size`, `mtimeNs` and `birthtimeNs`, because an inode number can be reused soon after a delete. A link (a dangling one too), a folder or another kind of file is `BUNDLE_FILE_UNSAFE`; nothing there is `null`.
- `writeBundleFile`: resolve the parent with `realpath` once and refuse if it is not the folder given; write the temporary file in that folder with a name that starts with a dot and ends in `.part` (a sync folder skips it) and holds at least 64 random bits, created with `O_CREAT | O_EXCL | O_NOFOLLOW` and mode 0600 at creation; remove it on any failure.
  - Without `replace`: `link(tmp, target)` then unlink the temporary name. `link` fails with EEXIST when anything is there, so a file made in between is never replaced. Never "check, then rename".
  - Where `link` fails with EPERM, ENOTSUP, EOPNOTSUPP, ENOSYS, EXDEV or EMLINK (exFAT and FAT sticks, some network shares, FUSE mounts and sync folders have no hard links): open the target itself with `O_CREAT | O_EXCL | O_WRONLY | O_NOFOLLOW` at mode 0600 (EEXIST is `BUNDLE_EXISTS`), keep the descriptor, `fstat` it for the identity, write, `fsync`, close, then unlink the temporary file. This path is not atomic: the file shows under its final name while it is written, and a crash can leave a truncated file, which the importer refuses because the revision does not match. If the write fails, `lstat` the target and unlink it only while its dev, ino and `birthtimeNs` still equal the identity taken and its size is the one the writer made (the bytes written once the write call has returned, else at most the bytes asked for). A file of another process, a reused inode and a file that someone made longer all stay. No `copyFile` (it gives no identity), and never `rename` without `replace`.
  - With `replace`: read the identity again right before the `rename` and refuse if it differs. A short window remains between that read and the rename.
  - A dangling link at the target, or a link or a folder made there after the first look, is `BUNDLE_FILE_UNSAFE` on both paths (an `lstat` after `EEXIST` tells a file from a link).
  - Errors are mapped by the code of the system error. `ELOOP`, `ENOTDIR`, `EISDIR`, `ENXIO`, `ENODEV`, a changed file and a path that is not the folder given are `BUNDLE_FILE_UNSAFE`. Every other system error (`ENOSPC`, `EACCES`, `EPERM`, `EROFS`, `ENAMETOOLONG`, `EIO`, `ENOENT`, …) is `BUNDLE_FILE_FAILED`, with a plain-words reason. The text of a system error, which names a path, is never passed on; its code is kept as `cause` (not enumerable, not in the message). An error with no system code is a defect, not a file fault: it is logged (a `BundleDefectWarning` process warning with the class name) and reaches the caller as `BUNDLE_FILE_FAILED` with the class name as `cause`, so no stray error type and no text that holds a path leaves the package.
  - The bytes are written in as many calls as the system needs (a short write is normal on a network share); a call that takes no byte is `EIO`.
  - The temporary file is removed on every failure, with three tries (0, 20 and 100 ms apart). A removal that still fails is a process warning (`BundleCleanupWarning`) with the code of the error and no path. The package deletes nothing in the person's folder except the `.part` file of the call that made it (and, in the no-hard-link path, the target that call created, only while the path still names that file by identity). A `.part` file left by a crash stays; the package does not sweep for it. In the no-hard-link path, if the removal of a failed write is declined or fails, or the identity was never read, a partial file can stay at the final name; the importer refuses it, and the warning says so.
- The tests of these rules are in `test/hostile-todo.test.mjs` (the file keeps its name from the stage 1 list of owed tests, and each entry keeps its name). The tests change the world at exact points through `setFileIoHook` in `src/file-io.ts`: swap a file, grow it, make `link` or a write fail. The function is not exported from `src/index.ts`, no code of the package calls it, and it throws unless `NODE_ENV` is `test`; the table of seams is not exported at all.

## Limits

`BUNDLE_LIMITS` in `src/limits.ts`: bundle file 48 MiB; 4,096 files; 1 MiB per file; 32 MiB in all; 16 folders and a file name in a path (17 segments); 1,024 characters per path and 255 bytes per segment; JSON depth 6; 200 notes names of up to 200 characters; 200 rows per preview list; 2 decoded bundles held in memory; 200 characters of a host or foreign-path text in a summary (cut); and for a tool, whole and never cut: a command or an argument of at most 4,000 characters and at most 64 arguments (`commandChars`, `toolArgs`; a bundle past either is refused, see Tools are shown whole); and the two work budgets (512 KiB of YAML, 3,000,000 scan places, see Work budgets). A definition at its own limits can pass 48 MiB once JSON escapes are counted. `encodeBundle` then refuses `BUNDLE_TOO_LARGE`, so export never writes a file that import refuses.

## Codes

Every refusal is a `BundleRefusal` with one of these codes. The words are `BUNDLE_MESSAGES` in `src/codes.ts`. The command line copies each sentence into `apps/cli/src/human.ts`, and `apps/docs/src/content/docs/reference/errors.md` repeats the same sentences. Save refusals (`SAVE_*`) pass through unchanged.

| Code | When | Words |
| --- | --- | --- |
| `BUNDLE_USAGE` | A choice names a notes name the bundle does not hold, a name is in both lists, or an argument is not allowed. | The choices do not fit this file, or a value of the call is not allowed. Nothing was written. |
| `BUNDLE_FORMAT` | The file is not JSON, not UTF-8, has a BOM, has a wrong or unknown format, a wrong shape, an unknown key, or a duplicate key. | This is not a Bowerloom harness file, or it is a form Bowerloom does not read. Nothing was written. |
| `BUNDLE_TOO_LARGE` | The file, the file count, one file or the total passes a limit. | This file is larger than Bowerloom reads, or it holds more files or bytes than a harness may. Nothing was written. |
| `BUNDLE_DAMAGED` | A size, a hash or the revision does not match the decoded bytes, or the base64 is bad. | This file does not match its own sizes or checksums, so it was changed or damaged. Nothing was written. |
| `BUNDLE_PATH_UNSAFE` | A path is not a plain path inside the harness. | This file names a path that is not a plain path inside the harness. Nothing was written. |
| `BUNDLE_SECRET_FOUND` | A file holds a literal secret value. | A file holds what looks like a secret value. A harness never carries one. Nothing was written. |
| `BUNDLE_INVALID` | The decoded files do not load as a harness. The loader's problems come with it, by path and code. Also: a tool's command, argument or hook command is longer than 4,000 characters, or a server has more than 64 arguments, so it cannot be shown in full (`TOOL_TEXT_TOO_LONG`). | The files in this bundle do not make a harness that loads. Nothing was written. |
| `BUNDLE_FILE_UNSAFE` | The bundle file is a link, not a regular file, not owned by the user, or changed while it was read. A write target is a link or a folder, or is not the file the person agreed to replace. | The bundle file is a link, is not a plain file that you own, or changed while it was read. Nothing was read or written. |
| `BUNDLE_FILE_FAILED` | The file could not be read or written for a reason of the system, not a fault of the file: the disk is full, read-only or failed, the name is too long, the file or folder is not there, or there is no permission. The refusal carries a plain-words reason after this sentence and the code of the system error as `cause`. | The file could not be read or written. The disk may be full or read-only, the name may be too long, or you may lack permission. Nothing was read or written. |
| `BUNDLE_EXISTS` | A write would put a file over a file that exists, and the caller did not ask to replace that file. | A file exists at that place already. Bowerloom does not replace it. Nothing was written. |
| `IMPORT_FOLDER_HAS_HARNESS` | The folder's harness has an entry, instructions, a source, knowledge, a script, an engine file, or a setting a person made (a description they wrote, an engine with a version or a model, an override, the settings of a skill). The refusal names what it found. | This folder has a harness with parts or settings in it already. An import goes only into a folder with no harness, or with an empty one. Nothing was written. |
| `IMPORT_NEEDS_ACKNOWLEDGEMENT` | An import has tools that run code or reach a host, files that can run, references in a url, argument, command or header, or paths from another computer, and the acknowledgement is missing or not the one the plan showed. | This file holds tools or files that can run, values it reads from this computer, or paths from another computer. Tick that you read them, then import. Nothing was written. |
| `EXPORT_NEEDS_ACKNOWLEDGEMENT` | An export has text that holds a path of this computer, and the acknowledgement is missing or not the one the plan showed. | These files hold a path from this computer. Tick that you read them, then export. Nothing was written. |

## Tests

`test/*.test.mjs` is in the root `npm test` (the repository's coverage test requires it). `test:harness-bundle` runs this folder alone.
