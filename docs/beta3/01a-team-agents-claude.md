Terms used below:

- A **harness** is an agent application that reads project files. The two harnesses are Claude Code and Codex.
- A **managed item** is one thing that `apply` installs and tracks, such as a skill or a prompt. This spec adds the kind `agent`.
- A **surface** is one place a managed item writes to, such as a file.
- A **hold** is a reported reason that one item is not applied. The rest of the plan still applies.
- A **refusal** stops the whole plan. Nothing is written.
- A **plan revision** is the 64-character hash that binds every input of a plan. Approval names it.
- A **subagent** is an agent that Claude Code starts for one task, defined in `.claude/agents/<name>.md`.
- A **role** is the file name of an agent without `.md`. A **team folder** is `.bowerloom/teams/<team>`.
- The **startup record** is the check that `bowerloom status` and `init status` run on a project (`inspectStartup` in `packages/startup/src/index.ts`).

## 2. Problem

`bowerloom apply` copies skills and prompts. It does not copy a team's agents. Claude Code reads subagents only from `.claude/agents/`. A team that defines its roles as agents has no working subagents after `apply`. The copies are ignored by git, so every new clone starts with none.

Example: the Sage Advice workbench keeps six research roles in `.bowerloom/teams/research-desk/agents/*.md`. I verified that `research-lead.md` there is a regular file of 3982 bytes with mode 0644. I did not find hand-made copies in the workbench checkout I looked at, so "the workbench copies them by hand" is the issue's account, not something I verified. The issue says one hand copy went stale, and `bowerloom status` reports the team folder as `edited` because no owner claims the `agents/` files.

## 3. Behavior

### 3.1 What apply does

1. Apply lists every team folder: each team in `.bowerloom/authoring/receipt.json`, and `first-team` when `.bowerloom/teams/first-team` is a real folder (decision 8). It reads `agents/` in each. It does this for every run, whatever `--harness` and `--team` say.
2. Apply checks the folders and files in the order of section 3.6.
3. Apply plans each valid agent as a managed item with id `agent_<role>`. The item has one surface, `agent-claude`, plus the catalog record.
4. The plan lists each agent with the same `up to date` or `update` line that prompts get. The agents are part of the plan revision.
5. After approval, apply writes one transaction per agent. It writes the Claude file and the catalog record together.
6. Apply never removes a copy. It never overwrites a copy that it did not install and that differs from the expected copy. It starts no process. It never fetches. The copy is `claudeCopyBytes(source)`. Today that function returns the source bytes unchanged.

The flag `--harness claude|codex|both` works like this:

- `claude` and `both` (the default) plan the agents.
- `codex` plans and lists no agent. Discovery, validation, `AGENT_LIMIT`, and the duplicate check still run, so a refusal still stops the plan. Per-agent holds are not listed. No catalog record of an installed agent shows as `kept`. If at least one agent file exists, the plan prints the Codex line of section 3.2.
- With `both`, the Codex line also prints when at least one agent file exists.
- The flag `--team <id>` (through `up --team`) filters only which agents are planned and listed. Validation, `AGENT_LIMIT`, and duplicates run over every team. The orphan scan uses the unfiltered set, so another team's installed agent is never shown as kept because of the filter.
- An agent item always has the harness list `['claude']`. The managed-item request check refuses any other list (section 6.1).

### 3.2 Plan lines, verbatim

`<role>` in a line is `role.padEnd(width)`, where `width` is the longest id in the plan plus one, as `apps/cli/src/apply.ts:66` computes it. Agent ids count toward `width`. `<pad>` is `''.padEnd(width)`. `<team>` is the team id. Item lines start with two spaces.

The title line (`apps/cli/src/apply.ts:69`) becomes the following when the harness list includes `claude`:

```
Apply skills, prompts, and agents for <harnesses>, team <team>
```

The `, team <team>` part appears only when a team is given, as today. Under `--harness codex` the title stays as it is today (`Apply skills and prompts for Codex`).

Per agent, state by state. The main line comes first, then the warning, then the notice, then a `Next:` line for a hold:

```
  <role> install agent: .claude/agents/<role>.md
  <role> update agent: .claude/agents/<role>.md
  <role> adopt agent: .claude/agents/<role>.md
  <role> agent up to date
  <role> agent kept: no longer an agent of this project, and apply removes nothing
  <role> agent held (<code>)
  <pad> Next: <next step>
```

State rules:

- `install`: no catalog record exists and the target file does not exist.
- `adopt`: no catalog record exists, the target file exists, and it passes every adopt test of section 3.3. The line says `adopt`, and the transaction does the work of section 3.3.
- `update`: a catalog record exists and either the inventory of the source differs from the catalog inventory, or the source path (the team) differs from the catalog source path.
- `up to date`: a catalog record exists and nothing differs.
- `kept` (state `orphaned`): a catalog record exists and no team folder, `first-team` included, holds a file named `<role>.md`, across all teams, whatever `--team` says. A deleted source file is this case. The copy and the catalog stay.
- `held`: see section 5.

The warning line, only for the actions `install`, `update`, and `adopt`:

```
  <pad> Warning: <role> is also the name of a built-in Claude Code agent. Check which one Claude Code uses.
```

The match is case-insensitive against the built-in names of section 4.2. The docs do not say how Claude Code ranks a project agent against a built-in, so the line makes no claim.

The notice line, only for the actions `install`, `update`, and `adopt`, and only when at least one item below applies. It follows the style of `noticeLine` in `apps/cli/src/apply.ts:36`:

```
  Note: agent <role> sets hooks and lists shell tools in tools. Claude Code applies them when the agent runs. Review .bowerloom/teams/<team>/agents/<role>.md.
```

The notice names these items, in this order, joined with `, ` and a final ` and `:

1. `sets hooks`, when the key `hooks` is present.
2. `sets mcpServers`, when the key `mcpServers` is present.
3. `sets permissionMode <value>`, when `permissionMode` is present and its value is not `default` and not `plan`.
4. `lists shell tools in tools`, when `tools` has an entry whose tool name is `Bash`, `PowerShell`, or `Monitor`. The tool name is the part before any `(`. The compare is case-sensitive. A pattern form such as `Bash(npm run *)` counts. Monitor runs commands, so it counts as a shell tool.
5. `inherits every tool, including shell tools`, when the key `tools` is absent.

The notice never quotes file text. `tools: []` is valid and gives no tool notice.

The Codex line, unindented, printed once after all item lines and before the `Network:` line (`apps/cli/src/apply.ts:71`), when `--harness` is `codex` or `both` and at least one agent file exists:

```
Codex agents are not projected in this beta. See the capability model design.
```

The pointer text (`packages/project-sync/src/apply-project.ts:44-58`) gains an agents sentence for the Claude harness:

- Claude only: `Project skills are in .claude/skills. Prompts are Claude Code commands in .claude/commands. Agents are in .claude/agents.`
- Both: `Project skills are in .claude/skills and .agents/skills. Prompts are Claude Code commands in .claude/commands, and Codex skills named prompt-<name>. Agents are in .claude/agents.`
- Codex only: unchanged.

The empty-plan text (`apps/cli/src/apply.ts:70`):

- When the harness list includes `claude`: `  Nothing in .bowerloom/skills.json, .bowerloom/prompts, or .bowerloom/teams/*/agents to apply yet.`
- Under `--harness codex`: the text of today, `  Nothing in .bowerloom/skills.json or .bowerloom/prompts to apply yet.`

Result words (`apps/cli/src/apply.ts:77-85`): the name function prints `agent <role>` for kind `agent`. The lines read `  agent <role>: installed`, `  agent <role>: updated`, `  agent <role>: held (<code>). Next: <next>`, and `kept, no longer listed: agent <role>`. An adopted agent counts as `installed`.

### 3.3 Adopt: how a hand-made copy becomes managed

The engine refuses an `install` when a surface already exists (`packages/managed-skills/src/v2-observed.ts:225`). A file surface is read with `surfaceV2` and `raw(p, 262144, false)`, which requires a regular file, one link, the owner uid, and mode exactly 0644 (`packages/managed-skills/src/observed.ts:92`). The transaction already moves any existing pinned surface to `old-<surface>` before it publishes the new one (`packages/managed-skills/src/v2-transaction.ts:301`). Adopt uses these two facts.

An agent is `adopt` when all of these hold:

1. No catalog record of the item exists.
2. A listing of `.claude/agents` holds exactly the name `<role>.md`, and no other name that equals it only after case folding.
3. `surfaceV2('agent-claude', 'file', <target>)` reads the file: a regular file, not a link, one link, owned by the user, mode exactly 0644, at most 256 KiB.
4. The sha256 of the file equals the sha256 of `claudeCopyBytes(source)`.

Then the action is `install`, and the engine accepts it. In `v2-observed.ts:225`, for kind `agent`, the check passes when every own surface is absent, except that `agent-claude` may be present as one file whose sha256 equals the sha256 of the closure file. The transaction moves the existing file to `old-agent-claude`, renames a byte-identical copy in, and commits. Rollback restores the original. The result counts the agent as installed.

If the file exists in any form that fails these tests, the agent is held with `AGENT_TARGET_OCCUPIED`, and nothing about it is written. The forms are: a link, mode 0600 or 0664, a foreign owner, more than one link, a folder, a file over 256 KiB, differing bytes, and a case alias. Adopt never applies when a catalog record exists. Then the normal drift rules apply.

### 3.5 Exit codes

They do not change (`apps/cli/src/apply.ts:99`):

- `0`: the apply finished, or there was nothing to change.
- `3`: approval is required.
- A refusal throws. The code is printed with its sentence and next step.

A hold is not a refusal. A plan with only holds prints `Nothing to change.` and exits 0. The six codes that this spec adds split like this:

- Holds (one agent): `AGENT_INVALID`, `AGENT_KEY_UNKNOWN`, `AGENT_NAME_MISMATCH`, `APPLY_AGENT_DUPLICATE` (both agents), and `AGENT_TARGET_OCCUPIED`.
- Refusal (whole plan): `AGENT_LIMIT`. An unsafe agents folder refuses with the existing code `AUTHORING_UNSAFE_PATH`.
- Also a refusal: `SKILLS_PROJECT_UNSAFE`, when `.claude` or `.claude/agents` is a link or is writable by the group or others (section 6.2).

A concurrent `apply` gets `MANAGED_SKILL_LOCKED`, as today.

### 3.6 Check order (precedence)

Apply checks in this order. The first refusal wins. Holds are collected, not thrown.

1. Listing. For each team folder, in team id byte order: `agents/` absent means no agents. If it exists, it must be a real folder owned by the user with no group or world write (`realFolder`, `packages/project-authoring/src/files.ts:22`), and its names must be safe (`folderNames`, `files.ts:28`). A failure refuses the whole plan with `AUTHORING_UNSAFE_PATH`.
2. `AGENT_LIMIT`: more than 128 entries in all agents folders together refuses the whole plan.
3. Per-file checks, in team-then-role byte order. A failure holds that agent: `AGENT_NAME_MISMATCH` for a bad file name or a `name` key that differs, `AGENT_KEY_UNKNOWN` for an unknown key, and `AGENT_INVALID` for every other read or parse failure.
4. Duplicates. Two valid agents with the same role in two teams hold both with `APPLY_AGENT_DUPLICATE`.
5. Target checks and state, per agent (section 3.3 and 3.2).

### 3.7 Write order and crash recovery

Apply keeps the order it has today (`packages/project-sync/src/apply-project.ts:181-215`):

1. Plan under the project lock. Refuse `STALE_APPROVAL` if the revision differs.
2. Create private folders.
3. Phase B for skills, then prompts, then agents. No project write happens in phase B. Agents are sorted by role in byte order.
4. Phase C, `applyChildren`, runs each child in the same order. Each agent child is one managed transaction. The transaction stages the Claude file and the catalog record, moves any existing target to `old-agent-claude`, renames the new files in, and commits the receipt last.
5. Interrupt: the signal is read between children, never inside one. Done agents are complete. Left agents are untouched. The message is `SKILLS_SYNC_INTERRUPTED` with `bowerloom apply` as the rerun command, as prompts do.
6. Crash inside a transaction: `.bowerloom/managed-pending.json` stays. The next plan refuses with `MANAGED_SKILL_RECOVERY_REQUIRED` and the next step `bowerloom skills recover plan --item agent_<role>`. Recovery resumes, abandons, or rolls back that one agent. A rollback after an adopt restores the hand-made file byte for byte.

## 4. Schemas and formats

### 4.1 Agent file validation

The function is `parseAgent(text, stem, team)`. It is pure and lives in `packages/project-authoring/src/agent-file.ts`, so both the authoring owner and project-sync import it. It returns `{ ok: true, agent }` or `{ ok: false, code, detail }`. A wrapper `parseAgentOrRefuse` calls `refuse(code)` (`packages/project-authoring/src/refusal.ts:42`) for the status verifier. `detail` is a fixed phrase, with a key name only when the key matches `^[A-Za-z0-9_.-]{1,64}$`. Any other key name is written as `a key with unsupported characters`. No message quotes other file text.

File rules:

- The folder `.bowerloom/teams/<team>/agents/` may hold only plain files named `<stem>.md`. A folder, another extension, a hidden name, a link, or a stem that fails the pattern holds that entry. The held item id is the entry name without a trailing `.md`.
- The planner reads each source file once, with `readLocalAgent` (section 6.1). The read rules are `authored` in `packages/managed-skills/src/local-source.ts:23`: a regular file, one link, the owner uid, no group or world write, at most `LIMITS.file` (65536 bytes). Any read failure holds the agent with `AGENT_INVALID`, naming the file.
- The text decodes with `new TextDecoder('utf-8', { fatal: true, ignoreBOM: true })`. A leading U+FEFF stays in the text, and `parseAgent` refuses it with `AGENT_INVALID`. A byte sequence that is not UTF-8 (for example `ED A0 80`) fails the decode and holds the agent with `AGENT_INVALID`.
- A null byte or a carriage return is `AGENT_INVALID`. The status verifier reads with `readGuarded(path, 65536)` (`files.ts:40`) and decodes the same way.
- The stem matches `^[a-z0-9]+(?:-[a-z0-9]+)*$`, has at most 64 characters, and does not start with `prompt-`. A bad stem is `AGENT_NAME_MISMATCH`.
- Role names of the whole project count at most 128 entries (`AGENT_LIMIT`).

Frontmatter rules:

- The first line is `---`. Trailing spaces and tabs on a fence line are allowed. The closing fence is the next line that matches.
- The block parses with `parseDocument(block, { uniqueKeys: true })` and `toJS({ maxAliasCount: 0 })`. A parse error, an alias, a merge key, a duplicate key, or a result that is not a map is `AGENT_INVALID`.
- The body is everything after the closing fence line. Remove every trailing line break. If the rest is empty or only white space, the file is `AGENT_INVALID`. Validation does not change the file. The copy is `claudeCopyBytes(source)`.

Allowed keys, in this order. The list was fetched from code.claude.com/docs/en/sub-agents on 2026-10-22 and is verified:

```
name, description, tools, disallowedTools, model, permissionMode, maxTurns,
autoCompactWindow, skills, mcpServers, hooks, memory, background,
omitClaudeMd, effort, isolation, color, initialPrompt, experimental
```

Any other key is `AGENT_KEY_UNKNOWN`. Keys are checked before values. A key whose value is `null` (an empty value) is `AGENT_INVALID` for every optional key.

Value rules. "Characters" means the JavaScript `string.length`.

- `name`: required string. It must equal the stem, or the code is `AGENT_NAME_MISMATCH`. It has at most 64 characters and no `:`. (Claude Code allows up to 256 characters. Bowerloom is stricter because the name is a file name.)
- `description`: required string, at least 1 and at most 2048 characters.
- `tools`, `disallowedTools`, `skills`: a comma-separated string or a list of strings. To split a string, cut at each comma outside parentheses, then trim each entry. `tools: []` is valid and means no tools. `tools: null` and `tools: ''` are `AGENT_INVALID`. Each entry is 1 to 128 characters. The list has at most 64 entries. An unbalanced `(` or `)` is `AGENT_INVALID`.
  - A tool entry matches `^[A-Za-z0-9_.:*-]+(\(.{0,100}\))?$`. So `Bash(npm run *)` and `Edit(/src/**)` are valid. Tool names are case-sensitive.
  - A `skills` entry matches `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
- `model`: string matching `^[A-Za-z0-9][A-Za-z0-9._:/\[\]-]{0,127}$`.
- `permissionMode`: one of `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan`, `manual`.
- `maxTurns`: integer, 1 to 10000.
- `autoCompactWindow`: integer, 100000 to 1000000.
- `mcpServers`, `hooks`: any YAML map or list. Depth at most 6, where the top map counts as depth 1. At most 4096 bytes when written as JSON. Bowerloom never reads their meaning.
- `memory`: `user`, `project`, or `local`.
- `background`, `omitClaudeMd`: boolean.
- `effort`: `low`, `medium`, `high`, `xhigh`, or `max`.
- `isolation`: `worktree`.
- `color`: `red`, `blue`, `green`, `yellow`, `purple`, `orange`, `pink`, or `cyan`.
- `initialPrompt`: string, at most 8192 bytes.
- `experimental`: a map with only the key `cacheTtl`, whose value is `5m` or `1h`.

A bad value is `AGENT_INVALID`, and the detail names the key.

### 4.2 Names

- One role name belongs to one team in a layer. Two valid agents with the same role in two teams hold both with `APPLY_AGENT_DUPLICATE`. The next step names both file paths. A role previously installed stays installed. Its copy is untouched.
- The built-in Claude Code subagents are `Explore`, `Plan`, `general-purpose`, `statusline-setup`, `claude-code-guide`, and `claude` (code.claude.com/docs/en/sub-agents, verified 2026-10-22). They live in one constant, `BUILTIN_AGENT_NAMES`, in `packages/project-sync/src/agents.ts`. A role that matches one case-insensitively gets the warning of section 3.2. The plan still applies it.

### 4.3 Tool names (for notices)

The verified Claude Code tool names (code.claude.com/docs/en/tools-reference, fetched 2026-10-22):

- Shell tools: `Bash`, `PowerShell`, and `Monitor`. Monitor runs commands.
- File-editing tools: `Edit`, `Write`, and `NotebookEdit`.
- Web tools: `WebFetch` and `WebSearch`.
- MCP tools: any name that starts with `mcp__`.
- `Agent` starts subagents.

`MultiEdit`, `BashOutput`, and `KillShell` are not in the current tool list. This spec does not name them. Only the notice rule uses these classes. Bowerloom does not refuse or hold on any tool name. A name in none of these classes is accepted and ignored.

### 4.4 Managed item and plan shapes

- Item reference: `{ kind: 'agent', id: '<role>' }`. Private folder name and catalog name: `agent_<role>`. The underscore is the reason: catalog names are parsed back into item references (`packages/managed-skills/src/v2-observed.ts:254-257`), and skill ids cannot hold an underscore (`packages/managed-skills/src/local-source.ts:14`). A skill named `agent-foo` can still exist and does not collide.
- Surfaces: `agent-claude` (a file) at `.claude/agents/<role>.md`, and `catalog` (a file) at `.bowerloom/managed/catalog/agent_<role>.json`. No `canonical` and no `projection-*` surface exists for an agent.
- Request source: `{ kind: 'agent', team, name }`, with the key list `['kind', 'team', 'name']`. `team` matches `ITEM_ID` (`local-source.ts:14`) and has at most 64 characters. `name` equals the item id.
- Closure source: `{ kind: 'agent', path: 'teams/<team>/agents/<role>.md' }`, with `closure.skill === null`. The closure file is `<role>.md` with the text `claudeCopyBytes(source)`. The inventory row holds that file's path, hash, and size. The `harnesses` list of the catalog is `["claude"]`.
- `claudeCopyBytes(source: string): string` is defined in `packages/managed-skills/src/agent-copy.ts` and re-exported from `packages/project-sync/src/agents.ts`. It returns `source`. `adopt`, `AGENT_TARGET_OCCUPIED`, and drift all compare against its output, never against the raw source. Spec 01b changes only this function.
- Types (in `packages/project-sync/src/agents.ts`, exported from `index.ts`):

```
type AgentState = 'new' | 'adopt' | 'edited' | 'up-to-date' | 'drift' | 'orphaned' | 'held'
interface AgentItem {
  id: string                       // the role, or the entry name of an invalid entry
  team: string | null              // null for an orphan
  itemId: string                   // 'agent_' + id
  state: AgentState
  action: 'install' | 'update' | 'none' | 'hold'
  harnesses: ['claude']
  expected: { files: InventoryRow[], surfaces: ItemSurface[], source: { kind: 'agent', path: string } | null }
  before: SyncItem['before']
  previousReceiptRevision: string | null
  history: number
  hold: { code: string, next: string } | null
  notices: string[]                // the five items of section 3.2, as keys
  builtin: boolean
  capabilities: null               // reserved for spec 01b
  enforcement: []                  // reserved for spec 01b
}
```

- State to action: `new` and `adopt` give `install`. `edited` gives `update`. `up-to-date` and `orphaned` give `none`. `drift` and `held` give `hold`.
- The plan gains `agents: AgentItem[]` and `codexAgentsSkipped: boolean`. `codexAgentsSkipped` is true when the harness list includes `codex` and at least one agent file exists.
- Format bump: the apply plan format changes from `bowerloom/project-apply-plan/v1beta1` to `v1beta2`, and the result format from `bowerloom/project-apply-result/v1beta1` to `v1beta2` (`packages/project-sync/src/apply-project.ts:38-39`). The bump stays in the Claude-only design. The plan gains `agents` and `codexAgentsSkipped`, and the result item kind gains `agent`. A reader that knows only v1beta1 would silently skip them. A new format string makes it fail loudly. Spec 01b fills `capabilities` and `enforcement` without another bump.
- Compatibility: the catalog regex of beta.2 (`v2-observed.ts:255`) throws on `agent_*.json`. A beta.2 CLI therefore refuses in a beta.3 project that holds an agent catalog. The release note says so.

### 4.5 Status ownership and the startup record

## 8. Migration from beta.2

Beta.2 never wrote `.claude/agents`. A project may hold hand-made files there.

On the first beta.3 `bowerloom apply`, for each agent:

1. The target file is absent. The agent is `install`.
2. The target file exists and passes the adopt tests of section 3.3. The agent is `adopt`. Bowerloom replaces it with a byte-identical copy and keeps the original as the operation backup until the operation commits. After the commit the file is managed.
3. The target file exists in any other form (differing bytes, wrong mode, foreign owner, link, case alias). The agent is held with `AGENT_TARGET_OCCUPIED`. The `Next:` line names the path. Nothing about that agent is written.

How the user releases a held file:

1. Move the file aside, for example `mv .claude/agents/research-lead.md .claude/agents/research-lead.md.old`.
2. Run `bowerloom apply`. The plan shows `install agent`.
3. Approve with `--approve <revision>`.

If the hand-made file holds edits the user wants, the user first copies those edits into `.bowerloom/teams/<team>/agents/<role>.md`, then moves the file aside. A file with mode 0600 or 0664 can also be fixed with `chmod 644`, if its bytes equal the copy.

Hand-made `.codex/agents/*.toml` files are not touched. Apply does not read, adopt, or hold them in this beta.

Bowerloom never edits `.gitignore` outside `.bowerloom/managed/.gitignore`. The agents guide tells the user to commit the source files and to decide for themselves whether git tracks `.claude/agents`.

## 13. Forward compatibility with 01b

Spec 01b designs a harness-neutral capability model and Codex agents. This spec keeps the door open:

1. **The source format does not change when Codex arrives.** The file stays `.bowerloom/teams/<team>/agents/<role>.md` in the Claude Code subagent format, with the same allowed keys. If 01b needs a harness-neutral key such as `capabilities`, adding it relaxes the `AGENT_KEY_UNKNOWN` hold. That is not a breaking change for existing files.
2. **One function makes the Claude copy.** `claudeCopyBytes(source)` returns the source today. `adopt`, `AGENT_TARGET_OCCUPIED`, drift, and the closure text all use it. 01b changes only this function. Because the closure inventory holds the copy bytes, a change of the function plans as `update`.
3. **The managed-item kind allows a second surface.** The kind is `agent`, the id is `agent_<role>`, and the receipt and catalog hold a `harnesses` list and a `surfaces` list. 01b adds surfaces by extending `ItemSurfaceId`, `ITEM_SURFACES`, `locateV2`, `materialV2`, and `STAGE_NAME`, and by loosening the harness check in `requestV2`. `locateV2` for kind `agent` takes its surface list from the item, so a role may have no `.claude/agents` file later. An installed agent then moves through the existing `harnesses-changed` path (`apps/cli/src/apply.ts:54`).
4. **Reserved plan fields.** Each `AgentItem` carries `capabilities: null` and `enforcement: []`, and `HeldItem` carries an optional `harness`. 01b fills them without another format bump.
5. **The Codex line is the one place to change.** When 01b lands, the line `Codex agents are not projected in this beta. See the capability model design.` is removed, and the planner starts to accept the Codex harness. `codexAgentsSkipped` is the switch.
6. **No Codex file is read or written now.** Hand-made `.codex/agents/*.toml` files stay untouched, so 01b can define how to adopt them.
7. **The private folder name `agent_<role>` is final.** 01b must not rename it, because receipts already use it.
8. **Apply starts no process.** A later command may run roles. Apply does not.
