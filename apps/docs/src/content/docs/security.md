## Read a refusal as a boundary

| Symptom | Safe next step |
| --- | --- |
| Stale approval | Re-plan with current inputs, review again, and approve the new exact revision. |
| Existing `.bowerloom/` | Inspect the installation; use revision rather than another fresh setup. |
| `revision-pending` | Preserve state and choose explicit resume or rollback with the original approval. |
| Identity or file drift | Inspect the changed path and bytes. Do not edit the receipt or bypass ownership checks. |
| Unconfirmed stop | Retain the original owner's evidence. Do not claim cleanup or enroll a replacement over uncertainty. |
| Missing native qualification | Keep execution held. A fixture or older path is not a fallback permission. |

## Trust and limits

Portable file validation does not sandbox a model. A trusted local tool server can retain host filesystem and network rights. Container policy and synthetic tests narrow a boundary but do not establish universal containment.

Prompts and model refusals do not replace external permission enforcement. Public unattended teams require independently reviewed security evidence before activation.

Keep credentials out of portable definitions. Use private bindings where a supported feature requires them. No parser here guarantees that arbitrary prose contains no secret.

## Getting useful help

Share the package version, command family, safe error code, expected action, and a sanitized description. Keep tokens, private paths, raw receipts and customer data out of public reports.

## Evidence and limits

The installed CLI trial accepted its bounded setup, disclosure, synthetic-stop and recovery paths. It did not accept native adapters, all19 framework acceptance groups, publication, or support activation. [Support status](/docs/status/) names the exact trial.
