title: "Permissions and exact approval"
description: "Keep proposals, installation, and execution separate."

## Three different decisions

1. A plan describes specific files or effects.
2. Exact approval permits the named operation with its bound inputs.
3. A result records what happened, including uncertainty.

A general request to work on a goal is not an exact approval for every later effect. Setup writes its reviewed files; it does not grant runtime authority.

## Review what changes

Check the selected project, team, file inventory, proposed access, operation revision, and known limits. Changes to the target, goal, template, or identity invalidate earlier setup approval.

A portable definition names capabilities. It does not contain a live credential or an installed permission grant. Keep private bindings and approval receipts separate.

## Model output is a proposal

Prompts, comments, tool descriptions, and imported content cannot grant permissions. Framework controls must enforce the boundary even when a model follows hostile instructions.

For uncertain external outcomes, retain evidence and reconcile the original attempt. Do not assume failure authorizes a second effect.

## Evidence and limits

Exact setup and local disclosure refusals passed the historical `0.7.0-alpha.0` installed trial at `cd62b530`. [Historical trial identity](/docs/status/#reviewed-setup-identity).
